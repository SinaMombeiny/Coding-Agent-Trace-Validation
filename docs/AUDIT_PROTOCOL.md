# Manual Evidence Audit Protocol (RQ2)

**Version:** 1.1 — 12 November 2026

## Purpose

The audit evaluates whether saved public GitHub traces support repository-level coding-agent use in a selected set of repositories. It does not attempt to prove that every commit classified as AI by the upstream pipeline was generated by an agent.

## Sampling frame

The RQ2 review contains 33 repositories selected from the 56 repositories with successful main-report rows:

- 23 repositories where `tool_use` and `commit_use` disagreed;
- 5 controls where both signals were true;
- 5 controls where both signals were false.

The controls were selected using `tool_use` and `commit_use` with seed `20261107`. `ignored_tools` did not define the control groups. The original 59-repository sample is a convenience sample drawn from the researcher's GitHub starred list; it is not a random or representative sample of GitHub.

## Keep three data layers separate

1. **Raw public records:** commit messages, co-author trailers, PR bodies, PR-to-commit SHA mappings, branch names, labels, repository file paths, and `.gitignore` entries.
2. **Upstream pipeline classifications:** values such as `AI`, `AI-FOLLOWUP`, `Human`, and `Bot` from `commit_stats_main.csv` when that file exists.
3. **Manual audit decisions:** a human-reviewed status with an exact source, SHA or PR number, and review note.

A raw `commit_list.csv` row has no AI/Human classification by itself. If `commit_stats_main.csv` is absent, the pipeline classification for that raw commit is `NOT_AVAILABLE`; it must not be converted to `Human`, `False`, or evidence of non-use.

## Upstream analysis gate and missing classification files

The inspected upstream implementation calls `is_commit_adopter` when the repository is sampled or has selected file/ignore signals. The gate returns true when at least one PR has an AI-related branch or label, a PR contains a commit with an AI-classified author, or a repository commit has an AI-classified author. Only after this gate passes does `compute_adoption_and_metrics` run and write `commit_stats_main.csv` and `commit_stats_files.csv`.

Within the resulting metrics, `commit_use` is set to true only when the `overall` commit ratio is present and greater than zero. Consequently, a repository can pass a PR-metadata gate without `commit_use` becoming true, and a repository that does not pass the gate can have raw commit data but no classification CSV.

The local review confirmed two examples:

- `georgd/EB-Garamond`: the saved clone has no commit on the available refs since 1 January 2025; `commit_list.csv` has only its header. Two PRs and two PR commit records are saved, but the PR records have no saved merge timestamp or merge SHA. The PR commit records remain inspectable and must not be erased from the evidence scope.
- `Fox-Fig/slipstream-rust-plus-deploy`: `commit_list.csv` contains 80 raw commit rows; the saved PR files contain zero rows. `commit_stats_main.csv` and `commit_stats_files.csv` are absent. The saved Git references contain 80 commits across refs and 61 on `master` since 1 January 2025. These raw commits are unclassified in the missing statistics file; they are not presumed Human.

These are data-availability and pipeline-gating cases, not confirmed non-use findings. The v2 helper scans raw commit and PR-commit messages even when `commit_stats_main.csv` is absent, while keeping the classification as unavailable.

## Evidence categories

### Direct public traces

Examples include:

- an exact, tool-specific `Co-authored-by` trailer in a commit message;
- an explicit `Generated with [tool]` or equivalent tool-generated signature in a commit message;
- an explicit coding-agent disclosure in a pull-request body, but only when the PR is associated with a saved commit SHA through `pr_commits.csv` or an exact `merge_commit_sha` match.

Direct evidence can support repository-level adoption. It does not automatically validate all pipeline-labelled commits or establish what fraction of code was generated by an agent.

The v2 helper uses a strict allowlist for known agent co-author identities. It does not use a human commit author's name, committer name, or a vendor email domain by itself as direct attribution. These allowlisted patterns are a conservative triage rule, not a complete catalogue of all agent identities.

### Indirect clues

Examples include:

- a branch name such as `codex/...`;
- a PR label naming a tool;
- a tool-related configuration or instruction file;
- a matching `.gitignore` entry.

These clues may guide manual review. They are not sufficient on their own to confirm use.

### Unclassified direct traces

A direct trace in `commit_list.csv` or `pr_commits.csv` may be visible even when there is no matching `commit_stats_main.csv` row. The trace can be recorded as raw public evidence, but its pipeline classification is `NOT_AVAILABLE`. It is not counted as a confirmed RQ3 miss unless an independently available pipeline classification shows that the same SHA was classified as non-AI.

### Unresolved cases

Use `pending` or `manual_review` when local evidence is insufficient or when required source files are missing. The absence of a recovered trace is not evidence that no agent was used.

Use `ambiguous` when indirect clues exist but direct evidence has not been established.

Use `supported` only after a human reviewer records the exact trace and its source. The label means repository-level adoption is supported within the inspected public evidence scope.

## Attribution and linking rules

- Do not classify a commit as AI-assisted solely because the human author's name contains a tool name (for example, `Jean-Claude`).
- Do not treat a vendor email domain alone (for example, `@anthropic.com`) as agent attribution.
- Prefer exact known agent co-author identities and explicit generated-with/by signatures.
- Do not link commits to PRs through generic `#123` references. Prefer exact SHA rows in `pr_commits.csv` or an exact `merge_commit_sha` match.
- A PR body disclosure without an exact saved commit relationship is not counted as a linked PR disclosure by v2.
- Keep pipeline-derived labels separate from independently inspected public traces.
- Record exact commit SHA, PR number, source field, and a concise trace excerpt in the manual evidence note.
- When a PR has no saved `merged_at` value, do not describe the PR as merged. Preserve the PR-level evidence and its merge-state limitation separately.

## RQ3 separation

A direct trace on a commit explicitly classified as `Human` or `Bot` by the upstream pipeline is an RQ3 candidate. A direct trace on a commit with no available classification remains unclassified; it is not counted as a confirmed missed classification.

## v2 helper behavior

`batch_audit_v2.py` is a read-only local triage helper. It scans available rows from:

- `commit_stats_main.csv` for upstream classification;
- `commit_list.csv` for raw commit messages;
- `pr_commits.csv` for PR-associated commit messages and exact SHA mapping;
- `pr_list.csv` for PR body disclosures, branch names, labels, and merge SHA;
- `evidence_inventory.csv` for previously collected file and `.gitignore` clues.

It never writes to the candidate CSV, evidence inventory, or upstream outputs. It writes separate summary, evidence, report, and run-manifest files under `audit/v2_outputs/`. It makes no network requests. The recommendations are triage candidates and require human review.

## Reproducibility and quality controls

- Keep upstream pipeline outputs immutable.
- Preserve v1 results and run v2 separately.
- Keep a copy of the candidate CSV before any manually approved edit.
- Record script version, input hashes, run time, input-file availability, and missing files.
- Sentinel values such as future timestamps and `-1` metrics must not be interpreted as real activity without source-level confirmation.
- Evidence inventory scripts organize local outputs. They do not independently validate the underlying traces.
- Every automatically generated recommendation requires human review before it becomes a manual audit status.
